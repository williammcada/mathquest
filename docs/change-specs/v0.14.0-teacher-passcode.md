# MathQuest v0.14.0 — Teacher passcode (change specification)

**Status:** Approved by William McAda on 2026-10-15 (Asia/Shanghai): "Yes. Otherwise, the kids are eventually going to figure it out, and they're going to be playing the games at home, which is going to lead to weird questions from parents. And the kids burning through my on-render hosting allowance."
**Baseline:** `implement/v0.13.0-controls-sound` `92fc437` (MathQuest 0.13.0, PR #15). Stacked on it so v0.13.0 can ship alone.
**Handbook:** U-01, U-02, U-03, U-07, U-12, U-13 (DEV is owner-only); S-03, S-04.

## Problem (v0.13.0 audit)

MathQuest has no teacher sign-in. Anyone who opens the site root gets the teacher setup screen, including "Developer tools" links to no-math practice games, and anyone can create a room (`POST /api/sessions`) with three self-written questions and play every game. Practice/DEV pages are public files with no check.

## Change

1. **One teacher passcode**, stored only as a Cloudflare Worker secret `TEACHER_PASSCODE` (at least 8 characters). Never in the repository.
2. **Server (Worker):** `POST /api/sessions` (create room) and `POST /api/engine-preview` (sample answers) require the passcode in header `x-mathquest-teacher`; new `POST /api/teacher-check` verifies it. Wrong passcode → 403; secret not set → 503 with a plain message. Constant-time comparison. Existing rooms, student joins, teacher links (`?teacher=` key) and gameplay are unchanged.
3. **Setup page:** the site root first asks for the teacher passcode ("Students: use the link your teacher gives you"). After it is accepted on that computer it is remembered there; "Forget passcode on this computer" is offered. Developer tools appear only after the passcode.
4. **Practice / DEV / review pages:** a full-screen passcode screen covers the page until the passcode is verified with the server (remembered on that device).
5. **Version:** frontend 0.14.0; Worker 0.14.0 — **Worker and frontend deploy together** (S-04), and the secret must be set before the Worker deploy.

## Limits (stated plainly)

- Practice pages are static files: the passcode screen stops ordinary use, but someone who downloads the files and edits them could bypass it. School iPads make that impractical; this is a deterrent, not encryption.
- Anyone who already has a live room's student link can still join that room while it is open (unchanged; the teacher ends rooms).

## Verification

Worker tests for teacher-check / sessions / engine-preview (no passcode, wrong, right, unset); frontend tests for the gate; browser check of the setup page and a practice page; GitHub CI. Live: set secret → deploy Worker → merge frontend → create a room with the passcode; student join unaffected.
